# BBA internal roadmap

[Español](ROADMAP.md) · **English**

Updated 2026-10-31. Version **2.0.0** consolidates transport, protocol, and isolation fixes; unifies CLI/MCP around declarative schemas; and adds twelve capabilities without additional external production dependencies. Scope, budget, and no-secret-persistence constraints remain. The objective is reproducible web/API research with a skill, local CLI/MCP engine, evidence, controlled evaluation, and authorized pilot. Automated detection, agent-assisted investigation, and clues must be distinguished. Neither a version number nor a successful lab run guarantees a critical bug on any target.

## Scope and release criteria

The project started with repeatable contracts and a two-account vulnerable/fixed BOLA lab, then added a scoped HTTP executor with durable SQLite checkpoints, offline HAR/OpenAPI/REA imports, isolated Chromium capture, semantic checks, scanner candidate import, MCP, and a frozen evaluation set. A documented vulnerability class is not automatically implemented. Tests requiring action outside policy remain inconclusive. REA handles client artifacts; permission to inspect an artifact does not authorize contacting its backend.

Release criteria require mandatory scope and secret checks to pass, fixed variants not to confirm, reproducible reports, working install/diagnosis/cancel/recovery/export, and no adapter that escapes authorized destinations or budgets. Tools whose effects cannot be constrained remain lab-only or import-only. Lab metrics must not be extrapolated to all systems. A pilot records scope, coverage, limits, and evidence; finding a bug is not a release condition.

## Chronology and evidence

- **1.0.0 pilot, 2026-10-29:** the internally authorized DCS website was tested with anonymous, scoped GET only, not a third-party bounty program. Six-page capture sent 6 GETs and blocked 366 browser requests without detected leaks. Two follow-up runs sent 5 GETs in total and stopped at `/xmlrpc.php` 301. No confirmed finding. WordPress and Elementor version hints were informational candidates, not proof of an outdated plugin. The pilot exposed missing redirect destination retention and configurable identification headers.
- **1.2.0 pilot:** strict TypeScript, 159 tests, and 36-module build were reported. A second bounded DCS pilot sent four public GETs, blocked 67 out-of-scope resources, and detected zero sink leaks or uncertain reservations. No forms, credentials, authorization boundaries, or payloads were tested on that site. The public website result does not establish safety or a public bounty program.
- **1.3.0 JWT:** the [Titan article](https://blog.faav.net/how-i-couldve-accessed-17-trillion-microsoft-records) motivated an own-account signature-integrity check, distinct from validation-error clues and estimates of data reach. A Swagger route or archived configuration is a candidate, never permission. The recorded verification passed 165 tests and a 37-module build with vulnerable/fixed labs, network rejection, resume bindings, import, MCP inventory, and packaging. No active tests ran against the article's service.
- **1.4.0 published-case studies:** a case manifest, current policy, imported surface, and historical clue lead to one bounded JWT candidate and a five-section draft. Ambiguous or excluded candidates stay offline. The recorded verification passed 170 tests and a 38-module build. It did not reproduce the original article's impact.
- **1.5.0 MCP and page structure:** `setup-mcp` previews, backs up, and registers an offline-first server; `inspect_web_page` projects links, forms, and scripts without values/query strings; `page_view` reads them offline. A DOM route does not expand scope. The recorded verification passed 172 tests and a 39-module build, including isolated Codex registration and synthetic DOM capture.
- **1.6.0 campaign:** a case ledger links scope, policy review, surface, profile, execution, and draft. Capture and execution require current declarations and shared budget, reserve action folders before requests, and block silent repetition after interruption. Recorded verification: 175 tests and 40-module build. No external service was actively tested in this phase.
- **1.7.0 resume:** `campaign_resume` checks matching scope/surface/profile and continues only unstarted steps; interrupted actions and uncertain reservations block unsafe repeats. Recorded verification: 176 tests and 40 modules, with loopback-only new requests.
- **1.8.0 semantic report:** findings separately explain issue, discovery, proof, reproduction, and remediation, preserving `confirmed`, `not-reproduced`, or `unresolved` and evidence IDs. Recorded verification: 176 tests and 40 modules.
- **1.9.0 bounded checks:** template arithmetic, owned callback, cache-correlated cross-account exposure, single-use race, and cross-origin form were added with exact rules, negative controls, owned resources, and five-section drafts. A policy copy can be hash-bound to the campaign decision, but its hash does not authenticate the policy or owner permission. Recorded verification: **194 tests without skips**, strict TypeScript, and 45-module build on synthetic loopback servers.

## Version 2.0.0

Three blocks followed the 1.9.0 baseline:

1. **Security, transport, and protocol fixes (13):** `SafeError` at CLI/MCP boundaries; RFC 6265 cookie characters; dual-stack public DNS pinning and incomplete-response detection; RFC 6901 array-index checks; Win32/SQLite transaction locks; out-of-band MCP `ping` and `notifications/cancelled` with `AbortSignal`; out-of-order concurrent budget-pair release; complete CSRF cookie handling; native JSON types in JWT checks; study `requestHeaders`; deadline checks before waits; WebRTC peer-connection freezing against Chrome 145+ STUN UDP leaks; RFC 3986 `pchar` (`:`, `@`) path support.
2. **Structure and developer experience (12):** declarative CLI command registry with `campaign|check|study` groups and command help; dependency-free schemas with JSON Schema projection and exact field paths; shared journal and cross-routed evidence/artifact views; safe recursive build; Ubuntu/Windows GitHub Actions CI; `producerVersion`; `--lang es|en`; scoped path prefixes, `{param}` templates, and `filter[id]`; Node `>=22.13.0`; Codex/Claude/Gemini MCP setup; native TypeScript ZIP packager; quarantined linear-time HAR projection.
3. **New checks, surface, and evidence (12):** semantic mutation/mass-assignment with before/after state on disposable resources; offline GraphQL and JS/SourceMap imports plus `graphql-check`; JWT `alg-none` and `expired-token`; OAuth `redirect_uri`; ephemeral in-memory auth bootstrap; 3xx `Location` classification without following; offline HackerOne/Bugcrowd/Intigriti/security.txt policy import with manual wildcard review; scanner-candidate plans; submission drafts with conservative CVSS v3.1/v4.0 and redacted `curl`; single-connection HTTP/2 race; Ed25519 key/sign/verify; read-only loopback HTML inspector with strict CSP.

## Remaining limits

The operator must verify current policy, business rules, and controlled accounts/resources and review proof and impact before reporting. Generic SQL/NoSQL/command confirmation, internal-destination SSRF, other CSRF request types, causal cache attribution, and other race workflows remain open. There is no functional parity with REA, which solves artifact/runtime analysis, and no guarantee of a critical finding on any arbitrary website or app. Lab evidence is not extrapolated to a real service. Third-party bounty program selection, if pursued, needs a current reward program, clear scope, test accounts, compatible rules, and a bounded plan. Sending a report requires the user's explicit authorization.
